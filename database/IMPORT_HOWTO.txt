================================================================================
STAGING.SQLITE — HOW TO BUILD, COPY, AND OPEN
================================================================================

WHAT THIS IS
------------
`staging.db` is the SQLite file your Streamlit app and Python ETL scripts use
(`database/staging.db`). It holds the `raw_*` tables that mimic what you would
eventually load from Oracle (via your mentor’s refreshed mirror DB).

Your mentor’s workflow (conceptual):
  Oracle (production) → periodic export / job → SQLite on work PC → you keep
  working with the same table names (`raw_master`, `raw_card_share`, …).


REGENERATE FROM CSV FILES IN THE REPO
--------------------------------------
From the `Project` folder:

  python build_staging_from_raw.py

Inputs (edit paths inside `build_staging_from_raw.py` if you move files):
  - data/raw/CARD_SHARE_ANCHOR_2026.csv
  - data/raw/WEEKLY_SERIES_2026_ANCHOR_NEW.csv  (or data/testing/NEW_WeeklyMonitor_Weeks1to22_Full.csv if present)
  - data/raw/real/MID_NULL_2026.csv             (optional → table `src_mid_fetch`)

The script also creates synthetic 2024–2025 monthly history by scaling the 2026
extract (demo only). Replace with real Oracle extracts when available.

Then refresh the ML mart:

  python 02_transform_and_ml.py


TABLES CREATED (MAIN)
---------------------
  raw_master        — one row per MERCHANT_GROUP (ANCHOR), EQUIP_TYPES, TOTAL_MID
  raw_card_share    — YTD-style aggregates for 2026 (dashboard + clustering)
  raw_card_history  — monthly totals per group (2024–2026, long)
  raw_target        — FY2026 targets (derived in demo from aggregates)
  raw_monitoring    — weekly roll-up (YTD_VOL, growth, …)
  raw_weekly        — long format: MERCHANT_GROUP, WEEK, WEEKLY_TRX/VOL/FBI
  meta_staging_build— build timestamp and notes
  src_mid_fetch     — terminal-level MID file (MERCHANT_GROUP nullable until matched)


COPY TO ANOTHER PC OR BACK UP
-----------------------------
Copy the whole file:

  Project/database/staging.db

No import step is required for Python: `sqlite3.connect("database/staging.db")`
opens the file directly. Keep the same relative path as in `app.py` / pages.


OPTIONAL: INSPECT WITH DB BROWSER FOR SQLITE
--------------------------------------------
1. Install “DB Browser for SQLite” (sqlitebrowser.org).
2. Open → choose `staging.db`.
3. Browse Data / Execute SQL.

OPTIONAL: EXPORT A TABLE TO CSV (sqlite3 CLI)
----------------------------------------------
  sqlite3 staging.db
  .headers on
  .mode csv
  .output raw_card_share.csv
  SELECT * FROM raw_card_share;
  .quit


OPTIONAL: MERGE INTO ANOTHER SQLITE FILE
----------------------------------------
To append into an existing DB (advanced), use `ATTACH` in SQL or export CSV and
load from your mentor’s canonical DB — avoid duplicate primary keys. For your
internship demo, keeping a single `staging.db` per project copy is simplest.


QUESTIONS FOR YOUR MENTOR
-------------------------
- How often Oracle → SQLite is refreshed.
- Exact table/column names in the real mirror (rename in `build_staging_from_raw.py`
  or in a small mapping view if they differ).
- Whether terminal-level MID (`src_mid_fetch`) should be joined to
  `MERCHANT_GROUP` with a mapping table maintained by the bank.
